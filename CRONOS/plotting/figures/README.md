# CRONOS figures

Rendered figures and the tools that produce them. Everything here is a **build
output**: no image in this directory was drawn, cropped, composited or retouched
by hand, and every one can be regenerated byte-for-byte from the command
recorded below. Edit the tool, not the PNG.

Design documents live in [`../doc/`](../../doc/README.md); this file covers only
what the pictures are and how to make them again.

## Running any of them

```bash
conda activate <a CRONOS env from the matrix in ../../README.md>
cd <repo>/CRONOS
CUDA_VISIBLE_DEVICES=<idle card> python plotting/<tool>.py
```

Any of the four envs works — these tools import ManiSkill and SAPIEN and nothing
from the VLA stacks, which is the only axis the env matrix varies.

Run from `<repo>/CRONOS`. Each tool puts itself on `sys.path` and imports
`envs.bridge_multi` to register `PickPlaceNxM-v1`, so the geometry, the camera
and the reset machinery in the figure are the ones training uses — not a
lookalike.

**All of these need a GPU. Only `--policy vla` loads a model.** One env is
~2.7 GB of VRAM with no policy weights; `--policy vla` adds SpatialVLA-4B at
bf16 for ~9 GB peak. Point `CUDA_VISIBLE_DEVICES` at an idle card and a
figure will not disturb a training run — but do check, because a busy card slows
the render by roughly 3x (measured on two RTX PRO 6000 Blackwell cards: a
2x320-step job took ~8 min on the idle one and ~40 min on one already at ~53%
utilization).

### Why there is no CPU-only mode

Asked and answered by experiment, so it does not get re-litigated. Both halves
of "GPU-free" fail independently on the current tree:

- **Physics on CPU.** `sim_backend="cpu"` reaches
  `envs/bridge_multi.py::_initialize_episode`, which calls
  `self.scene._gpu_apply_all()` unconditionally; `PhysxCpuSystem` has no
  `gpu_apply_rigid_dynamic_data`, and it raises. Supporting CPU physics is a
  change to `bridge_multi.py`, not to a tool.
- **Rendering on CPU.** SAPIEN's rasterizer is Vulkan. Mesa's software driver
  (lavapipe, present here as `/usr/share/vulkan/icd.d/lvp_icd.json`) loads but
  the device creation fails with `ErrorExtensionNotPresent`: lavapipe exposes
  neither `VK_KHR_external_semaphore_fd` nor `VK_KHR_external_fence_fd`, both of
  which SAPIEN requires.

What *is* GPU-free is everything under `plotting/plot_*.py` — those read CSVs and
never touch the sim. `version.py` is dependency-free for the same reason.

## `episode_boundaries.png` — episodic vs non-episodic reset

A 2x4 grid. Rows are the two reset modes; columns are the head and tail frame of
each of the first two episodes of a **single** environment (`num_envs=1`).

|  | ep1 head | ep1 tail | ep2 head | ep2 tail |
|---|---|---|---|---|
| **Episodic** (`--reset-mode per_episode`) | `env.reset()` | last policy step | **`env.reset()` — fresh draw** | last policy step |
| **Non-Episodic** (`--reset-mode none`) | `env.reset()` | last policy step | **inherited: = ep1 tail** | last policy step |

Column 3 is the entire figure. Under `per_episode` every episode opens with an
`env.reset()`, which with the training default `obj_set=rand` re-draws object
position and rotation — in the rendered sheet the plate, cloth and shovel all
move. Under `none` there is no reset after the first episode, so episode 2 opens
on the live scene and its head frame *is* episode 1's tail frame. Columns 1-2 are
identical between the rows on purpose: they are the shared baseline that makes
column 3 readable as a reset effect and nothing else.

See [`../doc/reset_modes.md`](../../doc/reset_modes.md) for what the mode means for
training, including the start-state drift that makes bare `noep` metrics
optimistic — a claim this figure illustrates the mechanism of but does **not**
measure.

### The scene

`configs/spatialvla_2x2_train.yaml`, one group named `default`: ketchup bottle
and kitchen shovel over yellow plate and cloth (`obj: [7, 2]`, `recep: [1, 2]`).

This is a *change of default*, not of picture. The figure was first rendered
against `four_group_sequential_2x2.yaml` group 0, which declares the same two
objects and the same two receptacles; the tool builds its reset options out of
nothing but those indices plus `--obj-set` and `--episode-id`, so the two configs
produce the identical options dict. Re-rendering `episode_boundaries.png` under
the new default and diffing against the committed image gives `max |diff| = 0`,
so the committed figure is unaffected and the reference command below still
reproduces it exactly.

The one-group file is the default because it is also the scene a checkpoint
should be shown on: `--policy vla` narrows the config to the selected group and
resizes it to one env, and a four-group config there would hand the single env
group 0's objects while silently dropping the other three groups' tasks from the
scheduler.

### The determinism guarantee, and how it is checked

Both rows are separate `gym.make` instances. They share episode 1 because they
are given the same reset seed and replay the same pre-generated action sequence,
not because the script copies frames between them. Since that is an assumption
about sim reproducibility rather than a structural fact, the tool verifies it and
prints the result:

```
[check] ep1 head across the two rows: identical
[check] ep1 tail across the two rows: identical
```

A nonzero diff there means the two rows' episode 1 diverged and **column 3 can no
longer be attributed to the reset mode**. The tool says so in the output rather
than leaving a subtly wrong figure behind. On the reference run (seed 0,
`--policy zero`, RTX PRO 6000 Blackwell) both are `identical`.

Note that the tool seeds *every* episodic reset explicitly, which training does
not — `envs/wrapper.py::reset` passes options but no seed, letting the ambient
torch RNG carry episode 2. That is the one deliberate deviation, and it exists so
the whole sheet is reproducible from `--seed` alone.

### What drives the arm

Three options, and they answer different questions.

**`--policy zero` (default).** The arm holds. The only thing that moves the
scene is the reset machinery itself, which is what the figure is about, and the
sheet has nothing else in it to misread. Use this one when the point is the
reset semantics.

**`--policy vla --ckpt <glob/episode_NNNN>`.** A trained checkpoint drives the
arm, so the tail frames are states a real policy produced and the non-episodic
row shows what that policy actually leaves for the next episode to start from —
the drift `doc/reset_modes.md` warns about, in pictures. `--ckpt` is normally
the only flag needed: `main.py` copies the run's `run_config.yaml` next to every
checkpoint it writes, and the tool reads the policy family, base model, unnorm
key and LoRA rank out of it. That matters more than convenience — a `vla_path`
that disagrees with the adapter loads without any error and gives a silently
wrong policy. `--vla-family` / `--vla-path` / `--vla-unnorm-key` /
`--vla-lora-rank` override individually, and each override prints what it
replaced.

Sampling is greedy (`--vla-temperature 0`), not eval's 0.6, because the two rows
have to share episode 1 — a sampling policy would diverge between them and make
column 3 unreadable. Pass a nonzero temperature and the determinism check will
tell you it broke, with that as the likely cause.

This is the only path that goes through `envs/wrapper.py::CronosWrapper`: a VLA
emits action *tokens*, and the wrapper's `_process_action` is what decodes them
into the 7-DoF command. Reimplementing that decode in this tool would be the
single most likely thing here to drift out of sync with training. The upside is
that this path tracks `main.py::run_rollout` closely — same wrapper, same
scheduler-driven task switch at each `--task-len` boundary, same EER.

**`--policy random`** is honest about what it is: seeded white noise, an
illustration, **not** a stand-in for a trained policy. Over a full 320-step
episode a bad draw sweeps every object off the table — which is exactly what
`episode_boundaries_random.png` shows, and why that file is filed as secondary.
Read it as "the arm disturbed the scene and the non-episodic row inherited the
disturbance", not as a finding about either mode.

One mechanical trap worth recording: the controller is
`pd_ee_target_delta_pose`, which integrates the *target* pose. Temporally
correlated noise (`--action-momentum` near 1) therefore random-walks the target
out of the workspace inside a single segment and parks the gripper against the
camera. White noise (`--action-momentum 0`, the default) stays near home. The
first attempt at this figure used momentum 0.85 on the theory that a smoother
walk would make the arm travel further; it did, straight out of frame.

A third source of real tail states, if a run already exists for the mode you
want: `glob/train_videos/rollout_ep<N>_seg<M>/` holds the frames training
recorded. `--policy vla` is for when no such run exists, or when the two modes
must share episode 1 exactly.

### What the figure deliberately leaves out

- **HSR and LSR are off.** The four reset dimensions are orthogonal
  (`doc/reset_modes.md`); this figure isolates the episodic one. `--no-eer`
  turns off the fourth (EER) if you want the robot left where the policy put it
  at segment boundaries.
- **EER is on**, matching the `--reset-robot` default, so the robot returns home
  at every `--task-len` boundary and `_settle(0.5)` nudges the objects. That
  settle is why the non-episodic row's ep1 tail and ep2 head are not bit-identical
  under the default `--tail-phase pre_eer` — the tail is read at the last policy
  step, *before* the boundary block. Use `--tail-phase post_eer` to read it after,
  which is literally the state `main.py` stashes in `_no_reset_obs`; the check
  line then reports `max |diff| = 0` (verified: seed 0, `--episode-len 80
  --task-len 40 --tail-phase post_eer`).
- **No task switching.** The scheduler is not driven, so the instruction never
  changes. Nothing in the frame would show it, and a random/zero policy cannot
  act on it.

### Knobs

| Flag | Default | Note |
|---|---|---|
| `--episode-len` / `--task-len` | 320 / 80 | Mirrors `main.py`; 4 segments per episode. Same divisibility assertion. |
| `--policy` | `zero` | `zero` or `random`; see above. |
| `--action-scale` / `--action-momentum` | 0.5 / 0.0 | `--policy random` only. |
| `--tail-phase` | `pre_eer` | Or `post_eer`. |
| `--seed` | 0 | Fixes the reset draws *and* the action sequence. |
| `--config` / `--group` | `spatialvla_2x2_train.yaml` / 0 | One group named `default`: `obj=[7, 2]` (ketchup_bottle, kitchen_shovel), `recep=[1, 2]` (yellow_plate, cloth). |
| `--ckpt` | — | Required by `--policy vla`. A `glob/episode_NNNN/` directory. |
| `--vla-temperature` | 0.0 | Greedy. Eval uses 0.6; that would break the shared episode 1. |
| `--vla-family` / `--vla-path` / `--vla-unnorm-key` / `--vla-lora-rank` | read from the checkpoint | Only needed when the checkpoint has no `run_config.yaml`, or to deliberately deviate from it. |
| `--obj-set` | `rand` | Matches training. `fixed` pins the pose to `--episode-id`, which collapses the episodic row's ep2 head onto its ep1 head — useful only if you want to show the reset *without* re-randomization. |
| `--no-eer`, `--no-tiles`, `--no-labels` | off | `--no-labels` butts the frames together with no captions, like the catalog sheets. |

## `segment_frames.png` — one checkpoint, two training horizons

Where `episode_boundaries.png` shows one reset boundary in detail, this shows
sixteen segments in a row under two values of `--episode-len` — the `T` in a run
tag. `scripts/train.sh` sets `T80` to `--episode-len 80` and `T1280` to
`--episode-len 1280`, with `--task-len 80` in every horizon, so:

```
T80     [seg0][seg1][seg2] ... [seg15]      16 episodes, 16 hard resets
T1280   [seg0  seg1  seg2  ...  seg15]       1 episode,   1 hard reset
```

A segment is 80 steps and one task in both rows. The only thing that differs is
how often `env.reset()` interrupts them, which is exactly what `T` controls.
Under `T80` every segment starts from a freshly drawn scene; under `T1280`
segment *k* starts from wherever the policy left segment *k-1*. That second case
is the start-state drift `doc/reset_modes.md` describes, here frame by frame
instead of inferred from a curve.

Output is `figures/segment_frames/` — **64 PNGs**, `T0080__seg07__tail.png` and
so on (the horizon is zero-padded so a directory listing sorts `T0080` before
`T1280`) — plus a 4-row contact sheet.

### The two things that make the rows comparable, both checked

**Same task sequence.** Both runs walk the scheduler one task per segment from a
fresh start, so segment *k* carries the same instruction in every horizon. This
is a property of the loop, not an assumption: the per-segment instruction is
recorded, printed in full, and diffed across the horizons.

```
[tasks] 16 segments:
         seg  0  put ketchup bottle on yellow_plate
         seg  1  put ketchup bottle on cloth
         ...
[check] task sequence T1280 vs T80: identical
```

**Same starting scene.** Segment 0 opens on the same seeded `env.reset()` in
every horizon, so its head frame is a shared baseline; the tool prints that pixel
diff too. A `DIFFERS` on either check means nothing downstream should be read as
a horizon effect, and the tool says so rather than leaving a plausible-looking
figure behind.

### A checkpoint is required

Unlike the episode-boundary figure — whose point survives with the arm held
still, because it is about the reset machinery — this figure is *about what the
policy leaves behind*, so there is nothing to show without a policy. `--ckpt` is
normally the only policy flag needed. For a checkpoint that still sits in its run
directory, the spec comes from `run_config.yaml`; for one **copied out** of it,
the tool falls back to PEFT's `adapter_config.json`, which carries the base
model, the LoRA rank, and — via `auto_mapping.base_model_class` — the policy
family:

```
[ckpt] no run_config.yaml — read adapter_config.json instead:
       policy=openvla (from OpenVLAForActionPredictionWithValueHead)
       base=openvla/openvla-7b unnorm=bridge_orig lora_rank=32
```

The unnorm key is the one field neither file records, and it is inferred from the
family: `openvla_train` looks up `bridge_orig`, `spatialvla_train`'s processor
publishes `bridge_orig/1.0.0`. Guessing wrong there is a `KeyError` at
`get_action_stats`, not a wrong number, so it fails loudly. Every field can still
be overridden with `--vla-family` / `--vla-path` / `--vla-unnorm-key` /
`--vla-lora-rank`, and each override prints what it replaced.

Sampling is greedy (`--vla-temperature 0`) so the horizons stay comparable. EER
is on, matching `main.py`'s `--reset-robot` default; HSR and LSR are off.

### `--repeats`: one scene, several trajectories

A single rollout conflates two things — what the policy does, and what this
particular rollout happened to do. `--repeats N` separates them: it re-runs a
horizon N times from the **same initial scene** and the **same task order**,
varying only the policy's sampling. The spread across runs is then the sampling
variance of one starting condition, which is what makes a claim like "T1280
drifts toward already-satisfied start states" a property of the policy rather
than an anecdote about one trajectory.

The split is enforced by seeding the global torch RNG twice per episode: once
*before* `env.reset()` from `--seed` (which fixes the scene), once *after* it
from `--action-seed` plus the repeat index (which fixes the sampling). So the
scene is a function of `--seed` alone and the actions of `--action-seed` and the
repeat index alone.

It requires a nonzero `--vla-temperature`, and refuses without one:

```
--repeats > 1 with --vla-temperature 0 would produce identical runs: greedy
decoding is a function of the observation alone, and the initial scene and task
order are deliberately held fixed across repeats. Pass a sampling temperature
(eval uses 0.6).
```

Afterwards it checks the converse — that the runs really did diverge — and
reports the first segment at which each repeat's tail differs from run 0's:

```
[check] seg 00 head, T1280 run 1 vs T1280 run 0: identical
[check] T1280 run 1 vs run 0: diverges from seg 00; final tail max |diff| = 156
```

`IDENTICAL trajectory` there would mean the sampling changed nothing and the
extra runs were duplicates. Frame names gain a run index only when `--repeats >
1` (`T1280__run02__seg07__tail.png`), so a single-run directory keeps the short
names.

Note that the repeats figure samples at temperature 0.6 while
`segment_frames.png` is greedy, so `T1280 run 0` there is *not* the same
trajectory as `T1280` in the greedy sheet. The initial scene is shared — both
seed 0 — but nothing after segment 0's head is.

### Reference command

```bash
cd <repo>/CRONOS
CUDA_VISIBLE_DEVICES=4 python plotting/render_segment_frames.py \
    --ckpt /path/to/checkpoint/seed0
# → figures/segment_frames/*.png (64) + figures/segment_frames.png
#   ~50 min, ~16 GB VRAM with OpenVLA-7B

# four T1280 rollouts from one initial scene, differing only in sampling:
CUDA_VISIBLE_DEVICES=4 python plotting/render_segment_frames.py \
    --ckpt /path/to/checkpoint/seed0 \
    --horizons 1280 --repeats 4 --vla-temperature 0.6 \
    --out-dir figures/segment_frames_T1280_repeats \
    --sheet figures/segment_frames_T1280_repeats.png
# → 128 frames, 5120 policy steps, ~90 min

# cheap shape check before committing an hour of GPU:
CUDA_VISIBLE_DEVICES=4 python plotting/render_segment_frames.py \
    --ckpt <dir> --segments 2 --task-len 10 --horizons 10,20
```

The committed frames are the seed-0 OpenVLA-7B checkpoint at
`/path/to/checkpoint/seed0` (base `openvla/openvla-7b`,
LoRA r=32) — a bare checkpoint directory with no `run_config.yaml`, which is why
the `adapter_config.json` fallback exists.

## `plotting/extract_run_frames.py` — frames out of a run that already ran

The other two render tools re-simulate. This one does not: `main.py` already
writes one mp4 per (episode, segment, env) under
`glob/train_videos/rollout_ep{E}_seg{S}/env{N}.mp4`, and this pulls frames out of
them by index. No GPU, no simulator, no policy — which also means it can only
show what a run actually recorded. To render a state no run produced, use
`render_segment_frames.py`.

```bash
cd <repo>/CRONOS
python plotting/extract_run_frames.py <run> --list
python plotting/extract_run_frames.py <run> --envs 6 --segments 1,5,9 --frames first
```

`<run>` may be the run directory, its `wandb/run-*` directory, or the `glob/`
directory — the script walks down to whichever holds `train_videos`. A run
directory containing two wandb runs (normal after a resume) is not guessed at;
it errors with both paths listed.

**Episode and segment are 1-indexed**, matching the directory names
(`save_video_segment` writes `rollout_ep{iteration+1}_seg{segment_id+1}`); env
indices are 0-based, as in the filenames. Selectors take `all`, comma lists and
`a-b` ranges, and asking for something the run does not have is an error rather
than a silent omission — a strip quietly missing segment 9 because the run
stopped at 8 is worse than a failed command. `--frames` takes `first` / `last` /
`mid` / `all` or explicit indices, negatives counting from the end.

Every extracted frame is annotated from `glob/rollout_success.csv` with the
group, task, direction and success of that exact (episode, segment, env), so the
output says what is in the picture:

```
[frame] ep01__seg05__env06__f000.png  (80 frames)  group_A · put ketchup bottle on cloth · success=0
```

`--sheet` additionally tiles the selection into a labelled contact sheet, rows by
env.

### What "the first frame" is — and is not

Training videos hold exactly `task_len` frames and every one of them is a
**post-step** observation (`main.py:1262-1268`, matching AutoRL). Frame 0 is the
state after the segment's first control step, **not** the state the segment
started from.

The segment's true initial state is not in the video at all. It is deliberately
not recorded: at a segment boundary the camera buffer is still stale relative to
HSR's respawn and EER's `reset_robot()`, so recording the pre-step observation
there would save a frame that does not correspond to the simulated state. If you
need what a segment began from, the nearest recorded thing is the previous
segment's last frame (`--segments <S-1> --frames last`) — which is before that
boundary rather than after it.

Eval videos are the opposite: `main.py:1042-1061` records pre-step observations
plus one final post-step frame, so they hold `segment_len + 1` frames and frame 0
*is* the initial state. `--kind eval` reads those, with `--eval-prefix`
(`in_domain` / `out_of_domain`) and `--eval-ep` selecting within an episode.

## `asset_catalog.png` — every asset, one render

25 objects and 17 receptacles on one shared 7x6 grid: 25 + 17 = 42 fills it
exactly, so both categories share rows and columns rather than sitting in
separate blocks. Nothing is stitched — one camera shot of one scene.

It deliberately does not go through `PickPlaceNxM-v1`: that env's
`3rd_view_camera` is the calibrated Bridge 640x480 sensor framing a ~15x15 cm
workspace, which 42 assets do not fit in, and every instance would also drag in
the arena mesh and the WidowX arm. Re-aiming that camera would mean touching the
training env. So the tool builds a throwaway render scene and loads meshes by the
same rules `BasePickPlace._build_actor_helper` uses — same file preference
(`textured.obj` → `.dae` → `.glb`), same `model_db` scale — which is what makes
the geometry shown the geometry the env simulates. Assets keep true relative size
and rest with their bounding-box bottom on z=0.

```bash
CUDA_VISIBLE_DEVICES=5 python plotting/render_asset_catalog.py
# the back view is the same call with the camera moved and --out redirected, e.g.
CUDA_VISIBLE_DEVICES=5 python plotting/render_asset_catalog.py --elev 62 --azim -90 \
    --out figures/asset_catalog_back.png
```

`--elev` / `--azim` place the camera above and off head-on so the grid recedes
and the assets read as solids rather than flat top-down silhouettes; the exact
pair used for the committed back view is not recorded, so treat the numbers above
as a starting point rather than a reproduction.

## `background_catalog.png` — every background, same scene

The same objects, receptacles, arm and poses under each available background, one
image per background, produced by one vectorized reset: the tool sets
`select_overlay_ids` to a different index per env, which is the same option
`CronosWrapper._build_options` derives from a group's `background: k` key.
`obj_set="fixed"` plus one shared `episode_id` pins object choice, position and
rotation identically in every env, so the background is the only thing that
moves.

Two things "background" does and does not mean here:

- **Background and table are not separate axes.** `more_table/imgs/*.png` are
  full 640x480 photographs containing both the table and the room behind it, and
  `_green_sceen_rgb` replaces every non-robot, non-object pixel with one of them.
  Swapping the index swaps both. (`GroupSpec.table` is parsed but read nowhere.)
- **Surface texture currently has no effect.** `more_table/textures/*.png` and the

## Conventions

**Regenerate, do not edit.** Every figure is reproducible from the command in its
section above plus the tool's defaults. If a figure needs to change, change the
tool — a hand-edited PNG silently stops matching the code it claims to depict.

**A figure states what it does not show.** Each section above lists the axes it
holds fixed. The episode-boundary sheet illustrates the mechanism of the
start-state drift documented in `doc/reset_modes.md`; it does not measure it, and
nothing here should be cited as if it did.

**Claims about the environment are checked against the code, not remembered.**
The CPU-backend and Vulkan findings above are recorded with the exact failure so
they can be re-tested rather than re-argued; both were reproduced on this tree
under a `torch==2.7.0+cu128` env with SAPIEN 3.0.0b1 and ManiSkill 3.0.0b20.

**These PNGs are not gitignored.** `.gitignore` excludes runtime outputs
(`wandb/`, `*.mp4`, checkpoints) but says nothing about `figures/`, so once
committed a regenerated figure shows up as a diff. Commit the tool change and the
regenerated image together.
